Two diffs, two questions

Two dots ask how two snapshots differ. Three dots ask what a branch changed.

You will name the two commits each diff compares, predict what git diff main..add-loader and git diff main...add-loader will cover before you run them, and check your prediction against Git.

A recipe that never got its reason

Since Lesson 2 this course has told you to review a branch with three dots: git diff main...HEAD. It never said what the third dot is for, or what goes wrong with two. That was fine while you wrote the code yourself. When an agent wrote it, the diff is how you judge the work, so you need to know exactly what the diff is comparing.

Every diff has two ends. The two commands differ only in where they put the left end. To say where, you need one new idea.

The merge base

Walk backwards through the history of main and of your branch. The most recent commit they both contain is their merge base: the point where the branch split off. Git's definition is "the best common ancestor(s) between two commits to use in a three-way merge."1 GitHub's docs describe it as "The most recent common commit of both branches (merge base)."3

One command prints it:

$ git merge-base main add-loader
394e8c73a0127ff8373d51eafb6b2ce45582bf06

The output is "a commit which is reachable from both" names by following parents.1 It is a full 40-character hash, and it is the same whichever name you put first.

The Git reference says the two-dot form "is synonymous to the earlier form (without the ..) for viewing the changes between two arbitrary <commit>." The three-dot form is "to view the changes on the branch containing and up to the second <commit>, starting at a common ancestor of both."2

Why "reversed"?

A diff is a recipe for turning the left end into the right end. Suppose someone adds a line to README.md on main after your branch split. The tip of main has that line. The tip of your branch doesn't, because the branch started before the line existed. To turn the left end into the right end, the recipe has to take the line out. So the two-dot diff prints it with a minus sign.

A red minus line in a two-dot diff doesn't mean the agent deleted anything. It can mean main gained that line after the branch split. If you review an agent's branch with two dots, you will blame it for undoing other people's work.

The three-dot diff avoids this. GitHub's docs put it this way: "Because the three-dot comparison uses the merge base, it focuses on 'what a pull request introduces.'"3 That's why "Pull requests on GitHub show a three-dot diff."3 The Files changed tab you've used since Lesson 4 is this lesson's right-hand column.

When the two are the same

If main hasn't moved since the branch split, the merge base is the tip of main. Both diffs then have the same two ends and print the same text. The distinction only matters once main moves. Lesson 11 is about that moment.

git log uses the dots differently. In git log main..HEAD from Lesson 6, two dots select a range of commits. In git diff the dots pick two endpoints, and the docs warn that there they "do not mean a range."2

Try it: predict, then check

The simulator has two new commands, git merge-base and git diff. It has no files, so its diff prints no diff text. It tells you which commits' changes the diff would cover and marks them on the graph: a square for the merge base, a shaded disc for changes the diff includes, and a dashed ring for changes it includes in reverse.

main has two commits. add-loader split from the second one and has two commits of its own. Before you press Enter on tasks 2, 3, 5 and 6, decide which commits will be marked. Then run the command and see whether you were right.

After task 5 the dashed ring sits on main's new commit: the two-dot diff has spread onto main. After task 6 the marks are back where they were in task 2. The branch didn't change, so the three-dot diff didn't either.

Check yourself

Which commit is the merge base of main and add-loader?

  • Their most recent shared commit
  • The newest commit on main
  • The first commit ever made
  • The newest commit on add-loader

The merge base is the best common ancestor: the latest commit that both histories contain. git merge-base main add-loader prints it.

git diff main..add-loader shows a README line being removed. The agent never touched the README. What is the likely cause?

  • main gained that line later
  • The agent secretly deleted it
  • Git lost the file's history
  • The diff ran on GitHub

Two dots compare the two tips. A line that landed on main after the split is missing from the branch's snapshot, so it shows as a removal.

When do the two-dot and three-dot diffs print exactly the same text?

  • main hasn't moved since the split
  • The branch has only one commit
  • Both branches were pushed to GitHub
  • The branch touches one file only

If main hasn't moved, the merge base is the tip of main, so both diffs have the same two ends.

Which diff does a pull request's Files changed tab show?

  • Three-dot, from the merge base
  • Two-dot, between the two tips
  • Only the latest commit's changes
  • Everything since the first commit

"Pull requests on GitHub show a three-dot diff": the merge base against the latest version of the head branch.
