## 1. Git branching concepts (Pro Git, ch. 3)

- A branch is "simply a lightweight movable pointer to one of these commits." — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)
- Branches are cheap: a branch "is actually a simple file that contains the 40 character SHA-1 checksum of the commit it points to… Creating a new branch is as quick and simple as writing 41 bytes to a file (40 characters and a newline)." — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)
- HEAD: "It keeps a special pointer called `HEAD`… In Git, this is a pointer to the local branch you're currently on." — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell#_create_new_branch)
- `git branch <name>` creates but does not switch: "The `git branch` command only _created_ a new branch — it didn't switch to that branch." — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell#_create_new_branch)
- The book notes "From Git version 2.23 onwards you can use `git switch` instead of `git checkout`" (`git switch -c new-branch`, `git switch -`). — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell#_switching_branches)
- Default name in the book: "The default branch name in Git is `master`." / "'master' branch in Git is not a special branch… the `git init` command creates it by default." — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)
- Current git-init docs: if no name is given, Git uses "the default name (currently `master`, but this will change to `main` when Git 3.0 is released). The default name can be customized via the `init.defaultBranch` configuration variable." Option: `-b`/`--initial-branch=<name>`. — [source](https://git-scm.com/docs/git-init)
- GitHub, by contrast: "By default, GitHub names the default branch `main` in any new repository." — [source](https://docs.github.com/en/pull-requests/reference/branches#about-the-default-branch)
- Fast-forward: when the commit you merge in "can be reached by following the first commit's history, Git simplifies things by moving the pointer forward because there is no divergent work to merge together — this is called a 'fast-forward.'" — [source](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging#_basic_branching)
- Three-way merge: "Git does a simple three-way merge, using the two snapshots pointed to by the branch tips and the common ancestor of the two." The result "is referred to as a merge commit, and is special in that it has more than one parent." — [source](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging#_basic_merging)
- Conflicts: "If you changed the same part of the same file differently in the two branches you're merging, Git won't be able to merge them cleanly." — [source](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging#_basic_merge_conflicts)
- Conflict markers: the book's example uses `<<<<<<< HEAD:index.html` … `=======` … `>>>>>>> iss53:index.html`; "the version in `HEAD`… is the top part of that block (everything above the `=======`), while the version in your `iss53` branch looks like everything in the bottom part." — [source](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging#_basic_merge_conflicts)
- To resolve: "run `git add` on each file to mark it as resolved. Staging the file marks it as resolved in Git." `git mergetool` "fires up an appropriate visual merge tool." — [source](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging#_basic_merge_conflicts)
- After merging, delete the branch with `git branch -d hotfix`. — [source](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging#_basic_branching)
- Remote-tracking branches: "references to the state of remote branches. They're local references that you can't move; Git moves them for you whenever you do any network communication." Names take the form `<remote>/<branch>`, e.g. `origin/master`. — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_remote_branches)
- "origin" has no special meaning: it "is the default name for a remote when you run `git clone`." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_remote_branches)
- `git fetch origin` "fetches any data from it that you don't yet have, and updates your local database, moving your `origin/master` pointer." `git fetch` "will not modify your working directory at all." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_pulling)
- `git pull` "is essentially a `git fetch` immediately followed by a `git merge` in most cases." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_pulling)
- Push a branch: `git push origin serverfix` means "Take my `serverfix` local branch and push it to update the remote's `serverfix` branch." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_pushing_branches)
- Tracking/upstream: checking out a local branch from a remote-tracking branch "automatically creates what is called a 'tracking branch' (and the branch it tracks is called an 'upstream branch')… If you're on a tracking branch and type `git pull`, Git automatically knows which server to fetch from." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_tracking_branches)
- Set the upstream afterwards with `git branch -u origin/serverfix` (`--set-upstream-to`). `git branch -vv` lists "what each branch is tracking and if your local branch is ahead, behind or both." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_tracking_branches)
- `git push -u` / `--set-upstream`: "For every branch that is up to date or successfully pushed, add upstream (tracking) reference, used by argument-less git-pull and other commands." — [source](https://git-scm.com/docs/git-push#Documentation/git-push.txt---set-upstream)
- Delete a remote branch with `git push origin --delete serverfix`; "all this does is to remove the pointer from the server." — [source](https://git-scm.com/book/en/v2/Git-Branching-Remote-Branches#_delete_branches)

## 2. Git command reference (git-scm.com/docs, Git 2.56.0)

- **`git switch` is NOT experimental any more.** Up to Git 2.50 the man page said "THIS COMMAND IS EXPERIMENTAL. THE BEHAVIOR MAY CHANGE." ([2.50.0 page](https://git-scm.com/docs/git-switch/2.50.0)). Git 2.51.0 release notes: "'git switch' and 'git restore' are declared to be no longer experimental." ([RelNotes 2.51.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.51.0.adoc)). The current page has no such warning. — [source](https://git-scm.com/docs/git-switch)
- `git switch`: "Switch to a specified branch. The working tree and the index are updated to match the branch. All new commits will be added to the tip of this branch." — [source](https://git-scm.com/docs/git-switch)
- `git switch -c <new-branch>`: "Create a new branch named <new-branch> starting at <start-point> before switching to the branch. This is the transactional equivalent of `git branch <new-branch>` and `git switch <new-branch>`." `-C` does the same but resets the branch if it already exists. — [source](https://git-scm.com/docs/git-switch#Documentation/git-switch.txt---createnew-branch)
- `git switch -`: "synonymous to `@{-1}`. This is often used to switch quickly between two branches, or to undo a branch switch by mistake." — [source](https://git-scm.com/docs/git-switch)
- Switching "does not require a clean index and working tree… The operation is aborted however if the operation leads to loss of local changes." — [source](https://git-scm.com/docs/git-switch)
- `git branch -d`: "Delete a branch. The branch must be fully merged in its upstream branch, or in `HEAD` if no upstream was set." `-D`: "Shortcut for `--delete --force`." — [source](https://git-scm.com/docs/git-branch#Documentation/git-branch.txt--d)
- `git branch -a`: "List both remote-tracking branches and local branches." — [source](https://git-scm.com/docs/git-branch#Documentation/git-branch.txt--a)
- `git branch -v`/`-vv`: "show sha1 and commit subject line for each head, along with relationship to upstream branch (if any). If given twice, print the path of the linked worktree (if any) and the name of the upstream branch, as well." — [source](https://git-scm.com/docs/git-branch#Documentation/git-branch.txt--v)
- New in Git 2.56: `git branch --delete-merged <pattern>` deletes "local branches whose configured upstream matches <pattern>, but only when their tip is reachable from that upstream." Release note: it removes "local branches that are already merged into their tracked remote-tracking branches." — [source](https://git-scm.com/docs/git-branch#Documentation/git-branch.txt---delete-mergedpattern), [RelNotes 2.56.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.56.0.adoc). (My inference, not in the docs: squash-merged branches are not "reachable", so the option probably will not delete them.)
- `git merge`: "Incorporates changes from the named commits (since the time their histories diverged from the current branch) into the current branch." — [source](https://git-scm.com/docs/git-merge)
- `--ff` (default): "When possible resolve the merge as a fast-forward (only update the branch pointer…; do not create a merge commit)." `--no-ff`: "Create a merge commit in all cases." `--ff-only`: "When not possible, refuse to merge and exit with a non-zero status." — [source](https://git-scm.com/docs/git-merge#_fast_forward_merge)
- `git merge --abort`: "Abort the current conflict resolution process, and try to reconstruct the pre-merge state." The docs advise to "always commit or stash your changes before running `git merge`." — [source](https://git-scm.com/docs/git-merge#Documentation/git-merge.txt---abort)
- Markers: "The area where a pair of conflicting changes happened is marked with markers `<<<<<<<`, `=======`, and `>>>>>>>`. The part before the `=======` is typically your side, and the part afterwards is typically their side." `diff3`/`zdiff3` (`merge.conflictStyle`) add a `|||||||` section showing the original. — [source](https://git-scm.com/docs/git-merge#_how_conflicts_are_presented)
- Resolving: "Edit the files into shape and `git add` them to the index. Use `git commit` or `git merge --continue` to seal the deal." — [source](https://git-scm.com/docs/git-merge#_how_to_resolve_conflicts)
- `git log --oneline`: "a shorthand for `--pretty=oneline --abbrev-commit` used together." `--graph`: "Draw a text-based graphical representation of the commit history on the left hand side of the output." `--all`: "Pretend as if all the refs in `refs/`, along with `HEAD`, are listed on the command line." — [source](https://git-scm.com/docs/git-log#Documentation/git-log.txt---graph). The book uses `git log --oneline --decorate --graph --all`. — [source](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell#_switching_branches)
- **Three-dot diff:** `git diff A...B` "is to view the changes on the branch containing and up to the second <commit>, starting at a common ancestor of both <commit>. `git diff A...B` is equivalent to `git diff $(git merge-base A B) B`." So `git diff main...feature` shows only what the feature branch changed. Two-dot `A..B` is the same as `git diff A B`. — [source](https://git-scm.com/docs/git-diff#Documentation/git-diff.txt-gitdiffoptionscommitcommit--path-1)
- `git worktree`: manages "multiple working trees attached to the same repository," so you can check out more than one branch at a time. — [source](https://git-scm.com/docs/git-worktree)
  - `add <path> [<commit-ish>]` checks out into `<path>`, "sharing everything except per-worktree files such as `HEAD`, `index`." If you leave out the commit-ish (and `-b`/`-B`/`--detach`), Git creates a new branch named after the last path component: `git worktree add ../hotfix` → branch `hotfix`. `-b <new-branch>` creates a new branch; `-B` resets one that exists. — [source](https://git-scm.com/docs/git-worktree#Documentation/git-worktree.txt-addpathcommit-ish)
  - A branch can be checked out in only one worktree at a time: by default `add` refuses when the branch is already checked out somewhere else (`--force` overrides). — [source](https://git-scm.com/docs/git-worktree#Documentation/git-worktree.txt-addpathcommit-ish)
  - `list`: the main worktree comes first, then linked ones, each with its revision and branch or "detached HEAD". `remove`: "Only clean worktrees (no untracked files and no modification in tracked files) can be removed. Unclean worktrees… can be removed with `--force`. The main worktree cannot be removed." `prune` cleans up metadata for worktrees whose directories are gone. — [source](https://git-scm.com/docs/git-worktree#Documentation/git-worktree.txt-remove)
- `git restore` (also no longer experimental since 2.51): "Restore specified paths in the working tree with some contents from a restore source." `--staged` restores only the index; `--source=<tree>` takes content from a commit or branch (by default HEAD with `--staged`, otherwise the index). — [source](https://git-scm.com/docs/git-restore#Documentation/git-restore.txt---staged)
- `git stash`: "Use `git stash` when you want to record the current state of the working directory and the index, but want to go back to a clean working directory." `pop` removes a stash and applies it; `apply` applies but keeps it; `list` shows entries like `stash@{0}`; `-u`/`--include-untracked` also stashes untracked files. — [source](https://git-scm.com/docs/git-stash#Documentation/git-stash.txt---include-untracked)

## 3. GitHub Docs: branches, PRs, merge methods, linking, conflicts

- Branches "let you develop features, fix bugs, or safely experiment with new ideas in a contained area of your repository." "A branch you create to build a feature is commonly called a feature branch or topic branch." — [source](https://docs.github.com/en/pull-requests/reference/branches#about-branches)
- You need write access "to create a branch, open a pull request, or delete and restore branches in a pull request." — [source](https://docs.github.com/en/pull-requests/reference/branches#about-branches)
- Default branch: "the branch that GitHub displays when anyone visits your repository… also the initial branch that Git checks out locally when someone clones… the base branch for new pull requests and code commits." — [source](https://docs.github.com/en/pull-requests/reference/branches#about-the-default-branch)
- "A pull request compares the proposed changes on the head branch with the base branch." — [source](https://docs.github.com/en/pull-requests/reference/branches#comparing-branches-in-pull-requests)
- "Pull requests on GitHub show a three-dot diff": it compares "the most recent common commit of both branches (merge base) and the most recent version of the topic branch." — [source](https://docs.github.com/en/pull-requests/reference/branches#three-dot-and-two-dot-git-diff-comparisons)
- Advice: "merge the base branch (for example, `main`) into your topic branch frequently… We recommend merging a pull request as soon as possible. This encourages contributors to make pull requests smaller." — [source](https://docs.github.com/en/pull-requests/reference/branches#merging-often)
- Repository admins "can merge pull requests on branches with branch protections enabled even if the pull request does not meet the requirements, unless branch protections have been set to 'Include administrators.'" — [source](https://docs.github.com/en/pull-requests/reference/branches#working-with-protected-branches)
- "Pull requests are proposals to merge code changes into a project." PR tabs are Conversation, Commits, Checks ("automated tests, builds, and other validations"), Files changed, and Findings. — [source](https://docs.github.com/en/pull-requests/reference/pull-requests#working-with-pull-requests)
- Draft PRs: "Draft pull requests cannot be merged, and code owners are not automatically requested to review them. Drafts are useful when you want to share work-in-progress without formally requesting reviews." — [source](https://docs.github.com/en/pull-requests/reference/pull-requests#draft-pull-requests). Mark ready via **Ready for review** or `gh pr ready`; "You can convert a pull request to a draft at any time." — [source](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/changing-the-stage-of-a-pull-request)
- PR refs: GitHub "creates temporary Git references that point to the pull request's head branch and, when possible, to a simulated merge result." — [source](https://docs.github.com/en/pull-requests/reference/pull-requests#pull-request-refs-and-merge-branches)
- Merge methods — [source](https://docs.github.com/en/pull-requests/reference/pull-request-merges):
  - **Merge commit** (default): "all commits from the feature branch are added to the base branch in a merge commit. The pull request is merged using the `--no-ff` option." — [#merge-your-commits](https://docs.github.com/en/pull-requests/reference/pull-request-merges#merge-your-commits)
  - **Squash and merge**: "the pull request's commits are squashed into a single commit." Choose it "when a pull request represents one logical change, especially if the branch includes many small fixup commits." Warning: "Squash merging works best for short-lived branches. If you keep working on the same head branch after a squash merge, later pull requests can include commits that were already squashed into the base branch." — [#squash-and-merge-your-commits](https://docs.github.com/en/pull-requests/reference/pull-request-merges#squash-and-merge-your-commits)
  - **Rebase and merge**: "all commits from the topic branch (or head branch) are added onto the base branch individually without a merge commit." GitHub's version "Always updates the committer information and creates new commit SHAs." — [#rebase-and-merge-your-commits](https://docs.github.com/en/pull-requests/reference/pull-request-merges#rebase-and-merge-your-commits)
  - Indirect merges: a PR is marked `merged` if its commits reach the base branch some other way, "even if branch protection rules on that pull request were not satisfied." — [#indirect-merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges#indirect-merges)
- Creating branches on GitHub: use the branch dropdown → "Find or create a branch…" → **Create branch**, or the Branches page → **New branch**. You can also create a branch from an issue. "You can only create a branch in a repository to which you have write access." — [source](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository#creating-a-branch)
- Deleting: deleting a branch that has open PRs closes those PRs. Deleting a merged head branch makes GitHub retarget dependent PRs to "the merged pull request's base branch." — [source](https://docs.github.com/en/pull-requests/how-tos/commit-changes/managing-branches-within-your-repository#deleting-a-branch)
- You can delete a PR's branch with **Delete branch** after the PR is merged or closed, and get it back with **Restore branch**. — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/deleting-and-restoring-branches-in-a-pull-request)
- Auto-delete: "You can have head branches automatically deleted after pull requests are merged in your repository." Path: Settings → General → "Pull Requests" → **Automatically delete head branches**. Needs admin. "Branch protection rules and repository rules can also prevent branches being automatically deleted." — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches)
- Closing keywords: `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`. Example: "`Closes #10`". Colons and uppercase work too ("`Closes: #10`, `CLOSES #10`"). — [source](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#linking-a-pull-request-to-an-issue-using-a-keyword)
- **Keywords only work when the PR targets the default branch:** "If the pull request targets *any other branch*, then these keywords are ignored, no links are created, and merging the PR has no effect on the issues." Keywords in commit messages close the issue once merged to the default branch. — [source](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue#about-linked-issues-and-pull-requests)
- Merge conflicts "often happen when people make different changes to the same line of the same file, or when one person edits a file and another person deletes the same file." The **Merge pull request** button stays off until they are resolved. — [source](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/addressing-merge-conflicts/about-merge-conflicts)
- On GitHub: "You can resolve simple competing line change conflicts on GitHub. For other conflicts, use the command line." Steps: **Resolve conflicts** → delete the markers `<<<<<<<`, `=======`, `>>>>>>>` → **Mark as resolved** → **Commit merge**. Warning: "Resolving conflicts on GitHub merges the entire base branch into the head branch." If the head branch is protected, you must create a new branch. A **Fix with Copilot** button appears if Copilot cloud agent is on. — [source](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-on-github)
- Command-line guide: [source](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/resolving-a-merge-conflict-using-the-command-line)

## 4. GitHub flow

- "GitHub flow is a lightweight, branch-based workflow." — [source](https://docs.github.com/en/get-started/using-github/github-flow#introduction)
- Steps (headings, verbatim): **Create a branch → Make changes → Create a pull request → Address review comments → Merge your pull request → Delete your branch**. — [source](https://docs.github.com/en/get-started/using-github/github-flow#following-github-flow)
  - Create a branch: "A short, descriptive branch name enables your collaborators to see ongoing work at a glance. For example, `increase-test-timeout` or `add-code-of-conduct`." "you create a space to work without affecting the default branch."
  - Make changes: "Your branch is a safe place to make changes… Your changes will not end up on the default branch until you merge your branch." "Ideally, each commit contains an isolated, complete change." Tip: "Make a separate branch for each set of unrelated changes."
  - Create a PR: "If you want early feedback or advice before you complete your changes, you can mark your pull request as a draft." "If you link with a keyword, the issue will close automatically when the pull request merges." "If your repository has checks configured to run on pull requests, you will see any checks that failed on your pull request."
  - Address review comments: "You can continue to commit and push changes in response to the reviews. Your pull request will update automatically."
  - Merge: "Branch protection settings may block merging if your pull request does not meet certain requirements."
  - Delete: "After you merge your pull request, delete your branch. This indicates that the work on the branch is complete and prevents you or others from accidentally using old branches." "You can always restore your deleted branch or revert your pull request if needed."

## 5. Protected branches and rulesets

- **Availability:** "Protected branches are available in public repositories with GitHub Free and GitHub Free for organizations. Protected branches are also available in public and private repositories with GitHub Pro, GitHub Team, GitHub Enterprise Cloud, and GitHub Enterprise Server." — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). So a student's **private repo on GitHub Free cannot use them**.
- "Rulesets are available in public repositories with GitHub Free and GitHub Free for organizations, and in public and private repositories with GitHub Pro, GitHub Team, and GitHub Enterprise Cloud." — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- A rule can control "whether collaborators can delete or force push to the branch and set requirements for any pushes to the branch, such as passing status checks or a linear commit history." "By default, each branch protection rule disables force pushes to the matching branches and prevents the matching branches from being deleted." Branch name patterns use `fnmatch` (e.g. `*release*`). — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#about-branch-protection-rules)
- "Only a single branch protection rule can apply at a time"; this limit does not apply to rulesets. — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#about-branch-protection-rules)
- Required reviews: "collaborators can only push changes to a protected branch via a pull request that is approved by the required number of reviewers with write permissions." Optional extras: dismiss stale approvals, require code-owner review, and require approval of the most recent push. — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging)
- Required status checks "must have a `successful`, `skipped`, or `neutral` status before collaborators can make changes to a protected branch." **Strict** (the "Require branches to be up to date before merging" box, "the default behavior for required status checks") vs **Loose**. — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging)
- Tip: if rules require specific checks, "make sure that job names are unique across all workflows." — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#about-branch-protection-rules)
- Other settings: conversation resolution, signed commits, linear history ("pull requests merged into the protected branch must use a squash merge or a rebase merge"), merge queue, required deployments, lock branch, bypass, push restrictions, force pushes, deletions. — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#about-branch-protection-settings)
- A ruleset is "a named list of rules"; you can have "up to 75 rulesets per repository." Compared with protection rules: "Multiple rulesets can apply to the same branch at the same time… You can change a ruleset's enforcement status without deleting the ruleset… Anyone with read access to a repository can view its active rulesets." When rules overlap, "the most restrictive version of the rule applies." Enforcement status is Active or Disabled. — [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rulesets-and-protected-branches)

## 6. GitHub Actions and branches

- `push` branch filter: "causes your workflow to run only when a push to a branch that matches the `branches` filter occurs." Patterns are globs (`*`, `**`, `+`, `?`, `!`). You cannot use `branches` and `branches-ignore` for the same event. — [source](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushbranchestagsbranches-ignoretags-ignore)
- `pull_request` branch filter: "you can configure a workflow to run only for pull requests that target specific branches", so the filter matches the **base** branch. Use `github.head_ref` in a conditional to filter on the head branch. — [source](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpull_requestpull_request_targetbranchesbranches-ignore), [events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-pull_request-workflow-based-on-the-head-or-base-branch-of-a-pull-request)
- Gotcha: "If a workflow is skipped due to branch filtering, path filtering, or a commit message, then checks associated with that workflow will remain in a 'Pending' state. A pull request that requires those checks to be successful will be blocked from merging." — [source](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpull_requestpull_request_targetbranchesbranches-ignore). Compare: "A job that is skipped will report its status as 'Success'." — [source](https://docs.github.com/en/pull-requests/reference/status-checks)
- `pull_request` event: `GITHUB_REF` = "PR merge branch `refs/pull/PULL_REQUEST_NUMBER/merge`"; `GITHUB_SHA` = "Last merge commit on the `GITHUB_REF` branch". By default it runs on activity types `opened`, `synchronize`, `reopened`. — [source](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)
- "Because `actions/checkout` uses `GITHUB_REF` by default, it checks out the merge branch. Your CI tests run against the merged result, not just the head branch alone." To test the head commit instead, use `github.event.pull_request.head.sha`. — [source](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#how-the-merge-branch-affects-your-workflow)
- "Workflows will not run on `pull_request` activity if the pull request has a merge conflict." — [source](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)
- Status checks: "GitHub Actions generates checks, not commit statuses." "If status checks are required for a protected branch, they must pass before the pull request can be merged." — [source](https://docs.github.com/en/pull-requests/reference/status-checks)
- GitHub CI doc: "GitHub runs your CI tests and provides the results of each test in the pull request, so you can see whether the change in your branch introduces an error." — [source](https://docs.github.com/en/actions/get-started/continuous-integration#about-continuous-integration-using-github-actions)

## 8. CI/CD concepts

- Fowler, "Continuous Integration" (updated 18 January 2024): "Continuous Integration is a software development practice where each member of a team merges their changes into a codebase together with their colleagues changes at least daily. Each of these integrations is verified by an automated build (including test) to detect integration errors as quickly as possible." — [source](https://martinfowler.com/articles/continuousIntegration.html)
- Practices (section names): "Everyone Pushes Commits To the Mainline Every Day"; "Every Push to Mainline Should Trigger a Build" ([#EveryPushToMainlineShouldTriggerABuild](https://martinfowler.com/articles/continuousIntegration.html#EveryPushToMainlineShouldTriggerABuild)); "Fix Broken Builds Immediately" ("nobody has a higher priority task than fixing the build"); "Keep the Build Fast", which targets a ten-minute build ([#build-fast](https://martinfowler.com/articles/continuousIntegration.html#build-fast)); "Make the Build Self-Testing". Kent Beck quote: "No code sits unintegrated for more than a couple of hours." — [source](https://martinfowler.com/articles/continuousIntegration.html)
- Fowler on CD: Continuous Delivery keeps the product releasable; Continuous Deployment automatically releases every build that passes to production. (Paraphrase from the WebFetch summary; get exact wording before quoting.) — [source](https://martinfowler.com/articles/continuousIntegration.html)
- Fowler, "Patterns for Managing Source Code Branches" (28 May 2020), pattern one-liners:
  - Mainline: "A single, shared, branch that acts as the current state of the product" — [#mainline](https://martinfowler.com/articles/branching-patterns.html#mainline)
  - Healthy Branch: "On each commit, perform automated checks, usually building and running tests, to ensure there are no defects on the branch" — [#healthy-branch](https://martinfowler.com/articles/branching-patterns.html#healthy-branch)
  - Mainline Integration: "Developers integrate their work by pulling from mainline, merging, and - if healthy - pushing back into mainline" — [#mainline-integration](https://martinfowler.com/articles/branching-patterns.html#mainline-integration)
  - Feature Branching: "Put all work for a feature on its own branch, integrate into mainline when the feature is complete." — [#feature-branching](https://martinfowler.com/articles/branching-patterns.html#feature-branching)
  - Continuous Integration: "Developers do mainline integration as soon as they have a healthy commit they can share, usually less than a day's work" — [#continuous-integration](https://martinfowler.com/articles/branching-patterns.html#continuous-integration)
  - Pre-Integration Review: "Every commit to mainline is peer-reviewed before the commit is accepted." — [#reviewed-commits](https://martinfowler.com/articles/branching-patterns.html#reviewed-commits)
  - Release Branch: "A branch that only accepts commits accepted to stabilize a version of the product ready for release." — [#release-branch](https://martinfowler.com/articles/branching-patterns.html#release-branch)
  - "Frequent integration increases the frequency of merges but reduces their complexity and risk." — [#integration-frequency](https://martinfowler.com/articles/branching-patterns.html#integration-frequency)
- GitHub "Continuous integration": "Continuous integration (CI) is a software practice that requires frequently committing code to a shared repository. Committing code more often detects errors sooner and reduces the amount of code a developer needs to debug." — [source](https://docs.github.com/en/actions/get-started/continuous-integration#about-continuous-integration)
- GitHub "Continuous deployment": "*Continuous deployment* (CD) is the practice of using automation to publish and deploy software updates. As part of the typical CD process, the code is automatically built and tested before deployment." A CD workflow can run "when new code is pushed to the default branch". Environments can "require approval for a job to proceed, restrict which branches can trigger a workflow." — [source](https://docs.github.com/en/actions/get-started/continuous-deployment#about-continuous-deployment)

## 9. Claude Code and git (code.claude.com/docs, current)

**Worktrees and the `--worktree`/`-w` flag (exists, documented)**
- CLI reference: "`--worktree`, `-w` | Start Claude in an isolated git worktree at `<repo>/.claude/worktrees/<name>`. If you don't give a name, Claude Code generates one. Pass `#<number>`, a GitHub pull request URL, or a GitLab merge request URL to fetch that PR or MR from `origin` and branch the worktree from it" — example `claude -w feature-auth`. — [source](https://code.claude.com/docs/en/cli-reference)

- Worktrees now have their own page, [Run parallel sessions with worktrees](https://code.claude.com/docs/en/worktrees). Common workflows keeps a short section: "Each git worktree is a separate checkout on its own branch, created from an existing commit, so the repository needs at least one commit first." In an empty repo the command fails with `Failed to resolve base branch "HEAD": git rev-parse failed`. — [source](https://code.claude.com/docs/en/common-workflows#run-parallel-sessions-with-worktrees)
- "Pass `--worktree` or `-w` with a name to create an isolated worktree and start Claude in it. - Tip: "Add `.claude/worktrees/` to your `.gitignore` so worktree contents don't appear as untracked files in your main checkout." — [source](https://code.claude.com/docs/en/worktrees#start-claude-in-a-worktree)
- A worktree is a fresh checkout, so install dependencies there. A `.worktreeinclude` file (gitignore syntax) copies gitignored files such as `.env` into new worktrees. — [source](https://code.claude.com/docs/en/worktrees#copy-gitignored-files-into-worktrees)
- Mid-session: you can ask Claude to "work in a worktree" and it uses the `EnterWorktree` tool. — [source](https://code.claude.com/docs/en/worktrees#ask-claude-to-create-a-worktree)
- Base branch: by default (`worktree.baseRef: "fresh"`) Claude branches "from the repository's default branch on the remote, usually `main`"; `"head"` branches from your current local HEAD. "You can't set `worktree.baseRef` to a branch name." — [source](https://code.claude.com/docs/en/worktrees#choose-the-base-branch)
- Cleanup on exit: if the worktree is clean, an unnamed session's worktree and branch are removed automatically. If it has changes or commits, Claude asks whether to keep or remove it ("Removing deletes the worktree directory and its branch, along with all the work in them"). Resume with `claude --worktree <name> --resume`. `-p` runs don't clean up. — [source](https://code.claude.com/docs/en/worktrees#clean-up-worktrees)
- Isolation: in a worktree session Claude Code blocks edits to the main checkout, commands whose working directory is the main checkout, and git redirects (`git -C`, `--git-dir`, `GIT_DIR`) into it. — [source](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation)
- Subagents can use `isolation: worktree` in frontmatter. `/batch` splits a large change "into 5 to 30 independent units" and runs each in its own worktree. — [source](https://code.claude.com/docs/en/worktrees#isolate-subagents-with-worktrees), [commands](https://code.claude.com/docs/en/commands)
- Manual alternative from the docs: `git worktree add ../project-feature-a -b feature-a`, then `cd ../project-feature-a && claude`, then `git worktree list` and `git worktree remove ../project-feature-a`. — [source](https://code.claude.com/docs/en/worktrees#manage-worktrees-manually)
- Desktop app: choose the **worktree** option when starting a session; you can set a branch prefix for worktree branches. — [source](https://code.claude.com/docs/en/desktop)
- Naming trap: `/branch [name]` branches the **conversation**, not git ("Create a branch of the current conversation at this point"). — [source](https://code.claude.com/docs/en/commands). The best-practices page suggests treating named sessions "like branches". — [source](https://code.claude.com/docs/en/best-practices#resume-conversations)

**Checkpoints vs git**

## 10. Jupyter notebooks and branches

- The notebook format "is defined with this JSON schema"; code cells store "a list of outputs associated with executing that code. They also have an execution_count." So re-running a cell changes the file even if the code didn't change (my inference from the schema). — [source](https://nbformat.readthedocs.io/en/latest/format_description.html)
- nbdime "provides tools for diffing and merging of Jupyter Notebooks", because "primitive line-based diff and merge tools do not handle well the logical structure of notebook documents." Latest version **4.0.4** (PyPI). Commands: `nbdiff`, `nbdiff-web`, `nbmerge`, `nbdime config-git`. — [source](https://nbdime.readthedocs.io/en/latest/)
- Git integration: `nbdime config-git (--enable | --disable) [--global | --system]` will "register nbdime with git for the current project (repository), or on the global (user), or sytem level." After that, `git diff` gives "the standard diff for any non-notebook files, but use nbdime's command-line diff for all `.ipynb` files"; "Nbdime will also be used for all merges on notebook files." Not every command uses it ("git add --patch will not use the driver"). The web tools are explicit: `nbdiff-web`, `git mergetool --tool nbdime -- *.ipynb`. Setup writes `.gitattributes` (`*.ipynb diff=jupyternotebook`). — [source](https://nbdime.readthedocs.io/en/latest/vcs.html#git-integration)
- Jupytext (latest **1.19.5** on PyPI): "Have you always wished Jupyter notebooks were plain text documents?… And get clear and meaningful diffs when doing version control?" A `py:percent` text notebook stores "Only the notebook inputs (and optionally, the metadata)… Text notebooks are well suited for version control." — [source](https://github.com/jupytext/jupytext#readme)
- Pairing: `jupytext --set-formats ipynb,py:percent notebook.ipynb`; sync with `jupytext --sync notebook.py` ("the inputs are loaded from the most recent paired file"); or put `formats = "ipynb,py:percent"` in `jupytext.toml`. — [source](https://github.com/jupytext/jupytext#command-line)
